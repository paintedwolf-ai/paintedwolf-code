# Comparing options

Use this when the human should pick one of several visual directions before implementation.

1. **Confirm a real fork exists** — options the user could reasonably prefer for different reasons. Do not stage a comparison to ratify a direction you already know is right; state that direction instead.
2. **Render every option on the same canvas** — identical `viewport.preset` and `theme` — so the differences the user sees are design, not framing. The preset holds the width; each option's height follows its own content. When the comparison is specifically about what fits above the fold, pin `viewport.fit: "viewport"` on all of them instead. Make options differ either by one variable (layout held constant, emphasis varies) or as coherent holistic alternatives; never a mix.
3. **Keep each option its own artifact.** Never composite variants into one image; each choice maps to exactly one artifact id. The compare card shows the options side by side and labels them A–D in order, so keep each legible at thumbnail size and give them the same aspect ratio. Two to four options; past four, cut the weakest yourself first.
4. **For a redesign, pair observed with proposed.** Capture the current state with `capture_page` `viewport: {width: 1280, height: 720}` and render the proposal with `viewport: {preset: "desktop", fit: "viewport"}` (or the matching width and height), and label which is observed runtime and which is authored intent. When the app's stylesheet lives in the repo, render proposals on it ([project assets](references/project-assets.md)) so options inherit the product's true look.
5. **Caption each option with a name and its claim** — `Option B — denser table, actions inline` — so the user's answer and your follow-up name the same thing.
6. **Issue one blocking ask** (read the ask-for-a-decision skill). As coordinator, call `ask_user` with `purpose: "compare"` and `artifacts: [A, B, …]` (2–4, in caption order) and no `options`; the host labels them A–D, so map each letter to its caption in `prompt`, and read the pick from `choices[]`. As a worker, call `request_decision` with the option names in `options` and the matching `artifact_ids` in the same order.
7. **Act on the answer once.** Build the chosen direction. A partial preference — one option with another's element — gets a single merged re-render confirmed the same way, not an open-ended redesign loop. Record the decision and its reason in prose.
